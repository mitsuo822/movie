## 1. 結論：推奨構成と進める順序

### 1.1 何を作るべきか

**「動画制作専用の1つのモデル」ではなく、「制作台帳（共通データ形式）を中心にした自動運転プログラム」を作り、モデルはその下で交換可能な部品として扱う**ことを推奨します。

理由は3つです。

1. **いま欠けているのはモデルの賢さではなく接続です。** 引き継ぎ情報では、台本制作も図解レンダリングも個別には動いており、欠けているのは「台本パッケージ→完成動画」の変換、動画生成の自動投入と結果取得、修正への接続です。これは学習では埋まらず、データ形式とプログラムで埋まります。
2. **16GBでは、主要モデルを同時に置けません。** 既存の Strata + Qwen3.8-Flash-Next IQ3_S は RAM+VRAM 合計 54.8GB、うち約50GBをRAMに置く構成です【一次: Strata docs/MODELS.md】。映像生成モデル側も量子化＋RAM退避が前提です。つまり「常駐する1つの頭脳」は物理的に成立せず、**工程ごとにモデルを入れ替える段取り**が設計の中心になります。
3. **専用学習は、教材と採点基準が先に必要です。** 何が良い出力かを測る検査と、失敗・修正の記録がない状態で学習しても、良くなったかどうかを判定できません。先に台帳と検査を作れば、その記録がそのまま教材になります。

### 1.2 全体構成

```
┌──────────────────── オーケストレーター（通常のプログラム）───────────────────┐
│  工程の状態管理 / 再開 / 失敗時の経路選択 / GPU排他スケジューラ / 実行台帳   │
└───────────────────────────────┬──────────────────────────────────────────────┘
                                │ すべての工程が読み書きする
                       ┌────────┴────────┐
                       │ 制作台帳（JSON）│  題材票 → 根拠 → 構成 → 台本 →
                       │  ＋素材フォルダ │  演出計画 → 素材 → タイムライン → 検査結果
                       └────────┬────────┘
   ┌──────────┬──────────┬──────┴─────┬───────────┬──────────┬──────────┐
 題材発見    調査      構成・台本    演出計画     素材生成     組立     検査・修正
 (データ取得 (検索・   (大型LLM)   (LLM→JSON)  図解/画像/   (Remotion) (プログラム
  ＋採点)    本文抽出)                          映像/音声              ＋小型VLM)
```

| 担当 | 何をやらせるか | 理由 |
|---|---|---|
| **通常のプログラム** | 工程管理、GPUの排他制御、形式検証、タイミング計算、字幕同期、レンダリング、決定的な検査（黒画面・無音・音量・はみ出し等）、修正の経路選択、台帳記録 | 正解が一意に決まる処理をモデルに任せると、失敗の原因が切り分けられなくなる |
| **大型ローカルLLM**（既存の Strata/Qwen3.8-Flash-Next を第一候補） | 題材の切り口出し、調査の要約、構成、台本、レビュー、部分修正 | 既に動いている資産。日本語長文の質が最も効く工程 |
| **小型マルチモーダルLLM**（Qwen3.5-4B/9B、Gemma 4 12B 級が候補） | 台本→演出計画JSONへの変換、映像プロンプトの生成と撮り直し時の書き換え、フレーム画像の点検 | 映像生成の合間に短時間で出し入れできる大きさが必要。ここが**専用学習の対象候補** |
| **画像生成モデル** | キャラクター表、キーフレーム、挿絵 | 人物・画風の一貫性は映像モデルではなく画像側で確保する（3.3節） |
| **映像生成モデル** | キーフレームから数秒のクリップ | 機種は実測の比較で決める（3.2節） |
| **音声** | ナレーション、台詞、BGM、効果音 | 解説はモーラ単位の時刻が取れるエンジンを優先（3.4節） |
| **Remotion** | 解説・生成映像の両方の最終組立 | 既存資産。両系統でタイムラインと字幕の仕組みを共有できる |

### 1.3 「単一モデルに学ばせること」の判断

- **学ばせない（プログラムとテンプレートで固定する）:** 台帳の形式、時間計算、字幕、図解部品の描画、検査の合否しきい値、修正経路。
- **学ばせる候補（小型モデルへのLoRA）:** ①台本の一節→演出計画JSON（図解の種類・要素・出現タイミング）、②ショット記述→採用した映像モデル向けプロンプト、および不良ラベルを受けた書き換え、③フレーム＋ショット仕様→不良ラベル（点検）。いずれも**入力と出力の形が狭く、回数が多く、映像生成の合間に走る**ため、小型化の利益が実際にあります。
- **当面は学ばせない:** 構成・台本の執筆そのもの。大型モデルが既に担当でき、文章工程は映像生成とGPUを取り合わない時間帯にまとめて実行できるため、小型化する理由が弱いです。
- **映像モデルの追加学習は今は選ばない:** 16GBは公表されている推奨をすべて下回ります（musubi-tuner: 映像学習は24GB以上推奨【一次】、LTX公式トレーナー: 標準80GB以上・低VRAM設定でも32GB想定【一次】）。一方、**画像LoRAは12GB以上推奨【一次: musubi-tuner】で射程内**なので、作風・人物の専用化は画像側で行います。

### 1.4 進める順序

| 段階 | 内容 | 次へ進む条件（実測） |
|---|---|---|
| **0. 棚卸し** | 既存 video-system を読み取りのみで確認し、台本パッケージの実際の形式、音声エンジン、Remotion部品を把握 | 既存の入出力形式が一覧化できた |
| **1. 接続** | 制作台帳の形式を決め、既存の台本パッケージ→演出計画→Remotion→MP4 を1コマンドでつなぐ。新モデルなし、3〜5分の解説で | 題材票1件からMP4が人手のコピーなしで出る |
| **2. 検査と修正** | 検査群と「既知の不良例」校正セット、修正経路表を解説系で作る | 各検査が校正セットで不良例を検出し、正常例を誤検出しない率を数値で出せた |
| **3. 映像モデル比較** | 候補モデルを同一課題で実測（ここで初めてダウンロード） | 16GBで「読み込める／実用速度／検査通過率」が候補ごとに出た |
| **4. 題材の自動選定と無人運転** | 題材発見→完成までの連続実行。尺を段階的に延ばす | 連続N本を無人で完走し、抜き取り確認で重大不良なし |
| **5. 生成映像系の最小版** | 台詞なし・人物一貫性を要求しない形式で30〜60秒の作品 | 撮り直し込みで完走し、歩留まりと所要時間が記録できた |
| **6. 人物の一貫性と台詞** | 画像LoRA／参照編集によるキーフレーム、口の動きの同期 | 同一人物判定の検査が校正セットで機能する |
| **7. 専用化・小型化** | 蓄積した記録で小型モデルを評価し、条件を満たした課題だけ学習 | 4章の判定条件 |

**解説系を先にする理由:** 既存資産があり、描画が決定的で、検査が作りやすく、そこで作る台帳・スケジューラ・検査基盤・音声・組立がそのまま生成映像系に流用できるためです。**段階3を段階2の直後に置く理由:** 映像モデルの実測結果が生成映像系の設計（尺、ショット設計、撮り直し回数）を決め、かつ制作過程の動画として最も見せやすい題材になるためです。

## 2. 解説動画と生成映像作品：共有する部分と分ける部分

### 2.1 共有する部分

- **制作台帳**（下記）と実行台帳（全工程の入力・出力・所要時間・検査結果の記録）
- オーケストレーター、GPU排他スケジューラ、再開機能
- 題材票、構成・台本の執筆とレビュー（既存 script-studio）
- 音声合成、読みの検査、字幕、BGM・効果音、音量調整
- Remotion による最終組立と書き出し
- 完成動画の検査、不良の修正経路、校正セット

### 2.2 分ける部分

| | 解説動画 | 生成映像作品 |
|---|---|---|
| 題材の根拠 | 出典つきの主張一覧（事実確認が必須） | 世界観・人物・画風の設定書（事実確認は原則不要） |
| 時間の主導権 | ナレーションの長さが画面を決める | ショット列・音楽の拍が先に決まり、語りは従 |
| 画面の実体 | 図解仕様（JSON）→ Remotion/SVG 部品 | キーフレーム画像 → 映像クリップ（複数テイク） |
| 結果の再現性 | 決定的（同じ入力なら同じ画面） | 確率的（歩留まりを前提に複数生成して選ぶ） |
| 主な不良 | 誤読、事実誤り、文字はみ出し、図と語りのずれ | 人物の変形、別人化、ちらつき、意図しない画面切替、指示との不一致 |
| 修正の基本 | 該当箇所だけ直して再レンダリング | 別シードで撮り直し→プロンプト書き換え→ショット設計の格下げ |

解説動画の中に生成映像を挿絵として入れる、生成映像作品に図解的な字幕を載せる、といった混在は、台帳上は「場面の種類」が違うだけなので同じ仕組みで扱えます。

### 2.3 制作台帳の骨格（案）

```jsonc
{
  "project": { "id": "...", "family": "explainer | generated", "target_sec": 240, "aspect": "16:9" },
  "topic":   { "title": "...", "angle": "...", "scores": { "demand": 0.0, "novelty": 0.0, "sources": 0, "visualizable": 0.0 } },
  "claims":  [ { "id": "c12", "text": "...", "sources": [ { "url": "...", "quote": "...", "fetched_at": "..." } ] } ],
  "bible":   { "style": "...", "characters": [ { "id": "ch1", "sheet": "assets/ch1.png", "voice": "..." } ] },
  "segments": [ {
      "id": "s03", "narration": "...", "claim_ids": ["c12"],
      "audio": { "file": "...", "morae": [ /* 開始・終了時刻 */ ], "reading_check": "pass" },
      "scenes": [
        { "id": "s03-a", "kind": "diagram", "template": "flow", "props": { }, "cues": [ { "word": "...", "show": "node2" } ] },
        { "id": "s03-b", "kind": "clip", "shot": { "subject": "...", "action": "...", "camera": "...", "must": ["..."], "must_not": ["..."] },
          "keyframe": "...", "takes": [ { "seed": 1, "file": "...", "checks": { }, "selected": false } ],
          "fallback": "still_motion" }
      ] } ],
  "qc": { "findings": [ { "check": "...", "target": "s03-b", "severity": "...", "route": "...", "attempt": 2 } ] }
}
```

要点は、**主張と出典、語りと時刻、ショットの「必ず映っているべきもの／映ってはいけないもの」を、後段の検査が照合できる形で最初から持たせる**ことです。検査は「台帳の記述」と「実際の出力」の突き合わせになります。

## 3. 技術選定と16GBでの実行方法

### 3.1 言語モデル

**現状確認できたこと**

- Strata は MITライセンスのローカル推論エンジンで、GPUに注意機構と頻用エキスパート、RAMに全エキスパート、SSDに参照表を置く方式です【一次: github.com/Niko1221/Strata】。
- Qwen3.8-Flash-Next は 125B総量／6B稼働の疎MoEと報告されています【二次】。GSQ-RCO は IST-DASLab の量子化手法（GSQ: Gumbel-Softmax量子化、RCO: サイズ予算下での層別ビット幅割当）です【一次: github.com/IST-DASLab/GSQ, /RCO】。
- IQ3_S は RAM+VRAM 54.8GB、「64GB RAMなら全サイズ載るが、IQ3_S は他をほとんど開けない状態で」と明記されています【一次】。RTX 5070 12GB + 64GB RAM で 53 tok/s の公表値があります【一次】。あなたの機材での値は未実測です。
- Flash-Next のライセンスは【未確認】（Apacheではないとする二次情報あり）。**収益化する動画に使う前に原文確認が必要**です。

**設計上の帰結**

- 大型モデルは「文章工程の専任」とし、**映像生成中は必ず降ろす**。IQ3_S の1段下（IQ3_XXS など）にすると常時の余裕が増える可能性がありますが、品質差は実測で判断します。
- 映像工程の合間に使う小型モデルは別に用意します。候補は次のとおりで、いずれも採用決定ではありません。

| 候補 | 規模・Q4_K_Mの大きさ | 画像/映像入力 | ライセンス | 備考 |
|---|---|---|---|---|
| Qwen3.5-4B | 約3.0GB【二次】 | 画像は llama.cpp で対応【一次】 | Apache-2.0【二次】 | QLoRAの公式ノートあり【一次: Unsloth】 |
| Qwen3.5-9B | 約6.2GB【二次】 | 同上 | Apache-2.0【二次】 | 10B未満の日本語評価で上位との二次情報 |
| Gemma 4 12B | 約7GB【二次・推定】 | 画像・音声【二次】 | Apache-2.0【二次】 | LTX-2.5のテキストエンコーダと同系統 |
| gpt-oss-20b | 約11.6GB【二次】 | テキストのみ | Apache-2.0【二次】 | 点検には使えない |

- **書き手と検査役を別系統のモデルにする**ため、小型側は Qwen 系と Gemma 系の両方を評価対象にします（6章の自己採点の偏り対策）。
- 出力形式は llama.cpp の `json_schema`／GBNF で拘束します。ただし「モデルはスキーマを見ていないのでプロンプトにも書くこと」「未対応のスキーマ機能は黙って無視される」と公式に注意書きがあります【一次: llama.cpp grammars/README】。拘束後にプログラムで再検証します。Strata が JSON スキーマ拘束と明示的なアンロードAPIを持つかは【未確認】で、段階0で確認します。

**区別して測ること**（1つの「動く」という言葉で混ぜない）

1. **読み込める:** エラーなく1本生成できる。最大VRAM・最大RAM・ページファイル使用量を記録。
2. **実用速度:** 「完成1秒あたりの生成秒数」と、モデル読み込み・退避の時間。想定する作品の尺×撮り直し倍率で一晩に収まるかで判定。
3. **望む品質:** 5章の検査の通過率と、通過したものの中であなたが選ぶ好み。
4. **追加学習できる:** 16GBで学習が最後まで走るか、学習後に改善が検査値に出るか。

**比較課題（同一条件で全候補に流す）**

静物・風景／ゆっくりしたカメラ移動／人物1人の単純動作／手と小物／2人の構図／イラスト調の画像を動かす／話す人物、の各分類で同じキーフレーム・同じ指示を使い、複数シードで生成します。課題数とシード数は、候補間の通過率の差が偶然の範囲を超えるかを見ながら増やします（最初から固定の本数を断定しません）。

**実行基盤**

- 第一案は ComfyUI のAPIです。`POST /prompt`、`GET /history/{id}`、`GET /view`、WebSocket、`POST /free`（`unload_models`, `free_memory`）、`POST /interrupt`、`/queue` をソースで確認しました【一次: server.py】。動的VRAM管理が標準で有効です【一次: cli_args.py】。API形式でのワークフロー書き出し手順は、今回は公式ドキュメントで再確認できていません。
- 代替は Wan2GP（キュー処理のヘッドレス実行、API、メモリプロファイル、Windowsインストーラあり）【一次】と、各モデルの公式スクリプトです。
- どれを使う場合も、オーケストレーターからは「ショット仕様とキーフレームを渡すとクリップと実行記録が返る」という同じ呼び出し口に包み、モデルを替えても上流が変わらないようにします。

### 3.3 画像生成と人物・画風の一貫性

- 候補: Z-Image-Turbo（Apache-2.0、16GBに収まる、8ステップ）【一次】、FLUX.2 klein 4B（Apache-2.0、約8GB、複数参照編集）【一次】、Qwen-Image-Edit-2511（Apache-2.0、複数画像入力、人物一貫性の改善を明記、VRAM公式値なし）【一次】。FLUX.2 の 9B と dev は非商用ライセンスなので対象外です【一次】。

### 3.5 16GBでのモデルの常駐と切り替え

**原則: 重いモデルは同時に1つ。切り替えはショット単位ではなく工程単位でまとめる。**

```
A 文章工程   : 大型LLM（RAM約50GB＋VRAM）      題材→調査→構成→台本→演出計画（全場面分）
  ── 降ろす（プロセス終了）→ nvidia-smi で解放を確認 ──
B 音声工程   : TTS（CPUまたは小VRAM）＋ASR      全セグメント合成→読み検査→辞書修正→再合成
C 画像工程   : 画像モデル                        全キーフレーム→小型VLMで点検→撮り直し
D 映像工程   : 映像モデル                        全ショット×複数テイク
  ── /free → 解放確認 ──
E 点検工程   : 決定的検査（CPU）＋小型VLM        テイク選別、撮り直し一覧を作成
  └ 撮り直しがあれば C/D へ戻る（上限回数まで）
F 組立工程   : Remotion（CPU主体）               書き出し→完成動画の検査
G 文章の修正が必要な不良だけ A に戻す
```

- 切り替えの実装: llama.cpp の llama-server はルーターモードで `/models/load`・`/models/unload`、`--models-max 1`、アイドル時の自動解放を持ち、モデルごとに子プロセスで動きます【一次】。llama-swap には ComfyUI との切り替え用の口があります【一次】。**確実な解放は「明示アンロード、だめならプロセス終了、その後 nvidia-smi で確認してから次を起動」**とします（プロセス分離からの推論で、公式の保証ではありません）。
- **RAMも排他対象です。** 大型LLMが約50GB、映像モデルの量子化版もRAMを大量に使うという報告があるため、スケジューラはVRAMとRAMの両方の空きを見て投入します。
- **並行できるもの:** Remotionの書き出し、決定的検査、TTS（CPU動作のもの）は、映像生成と同時に走らせられる可能性があります。実測でRAMが足りる範囲に限ります。
- **切り替え時間は実測項目です。** 大型LLMの読み込みに時間がかかるなら、Gの「文章へ戻る修正」は溜めてまとめて実行します。小型モデルで代替できる修正（プロンプトの書き換えなど）は工程D〜Eの中で完結させます。これが小型モデルを別に持つ実用上の理由です。
- 長時間の無人運転では、各工程の成果物を台帳に書いた時点で確定とし、途中で落ちても続きから再開できるようにします。

### 3.6 題材の発見と調査（インターネット取得とクラウドAIの区別）

**使うのはデータ取得だけで、生成は一切外に出しません。**

| 取得元 | 用途 | 注意 |
|---|---|---|
| Wikimedia Pageviews API（日本語版） | 関心の量と変化 | キー不要、利用者情報ヘッダ必須、データはCC0【二次】 |
| YouTube Data API v3 | 既存動画の分布、競合の有無、自チャンネルの実績 | 1日1万ユニット、検索は1回100ユニット【二次】。保存データの更新・削除規定あり |
| e-Stat、NDLサーチ、arXiv、J-STAGE、CiNii | 根拠資料 | 各サービスの利用条件、大量取得の禁止 |

| SearXNG（自前ホスト）＋ trafilatura（Apache-2.0）【一次】 | 調査時の検索と本文抽出 | 検索語とURLは外に出るが、文章生成はローカル |

## 4. 専用化・小型化：方式の比較と、選択を変える条件

### 4.1 比較

| 方式 | 得られるもの | 今回の評価 |
|---|---|---|
| **A. 既存モデル＋制作ツールの組み合わせ**（プロンプト、出力形式の拘束、テンプレート、プログラム検証） | 最短で一貫動作。失敗がそのまま教材になる | **最初に選ぶ。** 欠けているのが接続だから |
| **B. 小型モデルのLoRA**（狭い変換・点検課題） | 映像工程の合間に走る速さ、形式の安定、作風の固定 | **Aの記録が溜まり、下の条件を満たした課題だけ実施** |
| **C. 大型ローカルモデルの成果を小型へ移す** | Bの教材を大量に作れる | Bの教材づくりの手段として使う。ただし教師の出力は外部検証を通ったものだけ |
| **D. 画像LoRA**（人物・画風） | 作品の見た目の一貫性 | 参照編集で足りないと実測されたら実施。16GBで射程内 |
| **E. 映像モデルのLoRA** | 動きや質感の専用化 | 16GBは公表推奨未満。今は選ばない |
| **F. 小型モデルの全面的な追加学習** | — | 根拠となるデータも計算資源も不足。選ばない |

16GBでの学習の可否: Unsloth は Windows 対応で、4bit QLoRA の最小VRAMは 9Bで6.5GB、14Bで8.5GB、27Bで22GB とされています【二次・公式表のスニペット】。**おおむね14B級までが16GBの射程、27B級は不可**です。学習後は llama.cpp の `convert_lora_to_gguf.py` と `--lora` で読み込めます【一次】。学習中はGPUを占有するので、制作を止めて実行する夜間ジョブとしてスケジューラに載せます。

### 4.2 選択を変える実測条件

| 測るもの | 結果 | 判断 |
|---|---|---|
| 小型モデルの素の性能（形式の妥当率、検査通過率）を大型モデルと同じ固定評価セットで比較 | 差が小さい | 学習不要。プロンプトと例示で運用 |
| 同上 | 小型が明確に劣り、かつ誤りに一定の型がある | **B+C を実施** |
| 同上 | 小型が劣り、誤りがばらばら | 学習より課題の分割・テンプレート化を先に |
| 工程の所要時間に占める大型モデルの切り替え時間 | 小さい | 小型化の優先度を下げ、大型のまま |
| 学習量を段階的に増やしたときの評価値 | まだ伸びている | 教材を増やす |
| 同上 | 頭打ち | 追加しても無駄。モデル規模か課題設計を見直す |
| 学習後の固定評価セットの値 | 学習前より下がる項目がある | 採用しない（巻き戻す） |
| 画像LoRAなしの人物一致検査の通過率 | 十分 | Dは不要 |
| 映像モデルの比較結果 | どの候補も主要分類で歩留まりが実用に届かない | 生成映像系は「静止画＋動き付け」中心の形式に寄せる。機材の話はこの結果が出てから |

必要な教材数は断定しません。Unsloth の資料には「最低100行、1000行以上が望ましい」という目安があります【二次】が、これは一般論です。実際の必要量は、上の「段階的に増やして評価値の伸びを見る」方法で課題ごとに決めます。

### 4.3 教材：入力と正解例、作り方

| 課題 | 入力 | 正解例 | 正解例の出どころ |
|---|---|---|---|
| ①演出計画 | 台本の一節＋時刻＋使える図解部品の一覧 | 演出計画JSON | 検査を通過し、**修正を経た最終版**。修正前→修正後の対は特に価値が高い |
| ②映像プロンプト | ショット仕様＋キーフレームの説明＋（撮り直し時は不良ラベル） | 採用テイクを生んだプロンプト | 決定的検査を通過し、テイク選別で残ったもの。捨てたテイクは不良例として保存 |
| ③点検 | フレーム数枚＋ショット仕様 | 不良ラベル（なし／種類） | **人工的に不良を入れた例**（正解が確実）、決定的検査で確定した実不良、抜き取りで人が付けたラベル |

### 4.4 「モデルが合格と言った出力を教材にしない」ための規則

自己生成物での再学習は品質の劣化を招き得ること（Shumailov ら, Nature 2024）、LLMの採点役は自分の出力を高く評価する傾向があること（Panickssery ら, NeurIPS 2024）が報告されています（今回は書誌のみ確認、本文は未読）。そこで次を規則にします。

1. **教材に入れる条件は、モデル以外の証拠が最低1つあること。** プログラムによる検証の通過、人工不良のように正解が構造上確定しているもの、あなたの選択（好みのA/B）、抜き取り確認、公開後の実績、のいずれか。
2. **書き手と別系統のモデルの一致は「候補に残す」理由にはなるが、単独では教材の条件にしない。**
3. **固定評価セットは学習に一切使わない。** 正常例と不良例の両方を含め、学習前後・プロンプト変更前後で必ず同じものを流す。
4. **人が作った・人が選んだデータを捨てずに混ぜ続ける。** 自動生成の教材だけに置き換えない（蓄積で劣化を抑えられるという報告: Gerstgrasser ら）。
5. **教材には出どころを記録する。** どのモデルのどの版が作り、どの検査のどの版を通ったか。検査に欠陥が見つかったら、その検査を根拠にした教材を一括で外せるようにする。

### 4.5 失敗と改善の蓄積

実行台帳に、工程ごとに次を1件ずつ記録します：入力、出力、使用モデルと版、プロンプトの版、シード、所要時間、最大VRAM/RAM、検査結果、選んだ修正経路、修正後の結果。これにより、

- 「どの不良が、どの修正で、何回目に直ったか」が集計でき、修正経路表の優先順位を実績で更新できる
- 修正前→修正後の対が、そのまま課題①②の教材になる
- 捨てたテイクが課題③の不良例になる
- 既存の「検査用の指示文を比較・更新する自己改善」は、**校正セットに対する成績で指示文を選ぶ**形に組み込めます。重みは変えませんが、検査の精度を数値で上げる仕組みとして有効で、そのまま活かせます。

## 5. 自動検査と修正の具体設計

### 5.1 検査の原則

- 検査は「台帳に書かれた期待」と「実際の出力」の照合として定義する。
- **決定的に測れるものはプログラムで測る。** モデルによる点検は、プログラムで測れない項目に限り、はい／いいえで答えられる具体的な問いに分解する。
- 映像言語モデルは生成映像の物理・人体の誤りを見落とすという報告があります【二次】。**VLMの点検は「ふるい」であって最終判定ではない**ものとして扱い、複数テイクからの選別と、失敗しやすいショットを最初から設計で避けることを併用します。

### 5.2 検査と修正の具体例

| # | 不良 | 入力 | 照合相手 | 方法 | 修正先と直し方 |
|---|---|---|---|---|---|
| 1 | 台本の数値が出典と違う | 台本の一節、主張ID、出典の引用文 | 取得済みの出典本文 | 数値・年・固有名詞をプログラムで抽出し、引用文に同じものがあるか完全一致で確認。意味の一致は**書き手と別系統のモデル**に、根拠箇所の引用を必須にして判定させる | 台本工程：その一節だけ再執筆（既存の部分修正）。出典が見つからなければ主張を削除 |
| 2 | ナレーションの誤読 | 合成音声、台本の期待読み | 形態素解析で得た読み（かな） | 音声認識→かなに正規化→期待読みと比較。不一致区間を特定 | 音声工程：ユーザー辞書に登録、またはその語をかな表記にして**その文だけ**再合成 |
| 3 | 図の文字がはみ出す・重なる | Remotionで書き出した静止画、要素の座標 | 画面の安全領域、他要素の矩形 | 要素の外接矩形をプログラムで比較。OCR結果と期待ラベル文字列を照合 | 演出計画：改行位置・文字サイズ・配置の値を調整して再描画。規定回数で直らなければ図解部品を別の型に変更 |
| 4 | 図の出現が語りとずれる | 演出計画の合図、モーラ時刻 | 該当語が話される時刻 | 合図の時刻と発話時刻の差を計算 | 組立：時刻を再計算（モデル不要） |
| 5 | クリップ内の意図しない画面切替・静止・黒画面 | 生成クリップ | 「1ショット＝切替なし」という仕様 | 場面切替検出、静止検出、黒検出 | 映像工程：別シードで撮り直し |
| 6 | ちらつき・形の崩れ | 生成クリップ | 同じ分類の正常例の統計 | フレーム間差分や動きベクトルの異常値、先頭フレームとキーフレームの類似度 | 別シード→動きを弱める指示に書き換え→クリップを短くする |
| 7 | 人物が別人になる | クリップから抜いたフレームの人物領域 | 人物表 | 特徴量の類似度（終始の変化も見る） | キーフレームから撮り直し→人物が小さく映る構図に変更→別カットに差し替え |
| 8 | 指示と内容が違う | 抜き出したフレーム、ショット仕様の must / must_not | 仕様から機械的に作った問い（「人物は1人か」「提灯を持っているか」「文字が映っていないか」） | 小型VLMが問いごとに はい／いいえ を形式拘束つきで回答 | プロンプトを書き換えて撮り直し |
| 9 | 完成動画の音量・無音・音ずれ | 完成MP4 | 目標音量、台本、字幕時刻 | 音量測定、無音区間検出、完成音声を認識して台本・字幕時刻と照合 | 組立：音量調整、該当区間の再配置 |
| 10 | 場面が抜けた・尺が違う | 完成MP4、タイムライン | 台帳の全場面一覧 | 長さ、場面数、認識文と台本の対応 | 欠けた場面だけ再レンダリング |

7番の人物照合について：広く使われる InsightFace の学習済みモデルは非商用研究限定です【一次】。収益化を前提にするなら使えない可能性が高いので、ライセンスの明確な特徴抽出モデルを段階6で選びます。なお ffmpeg の各検出フィルタは今回公式文書を読めていないため、仕様は実装時に確認します。

### 5.3 必ず完成させるための「格下げの階段」

生成映像は撮り直しても直らない場合があります。各ショットに予備経路を持たせ、**無人でも必ず完成に到達**させます。

```
別シードで撮り直し（上限回数）
 → プロンプト書き換え（不良ラベルに応じた定型の対処）
 → ショットを単純化（動きを減らす、人物を小さく、尺を短く）
 → 静止画＋カメラの動き（Remotionで付ける。決定的で必ず成功）
 → その場面を別の場面に統合、または削除（台本工程に戻す）
```

どの段で止まったかは台帳に残り、次の題材の演出計画で「このモデルが苦手な型」を避ける材料になります。

### 5.4 検査そのものの検査（校正セット）

検査が役に立つと言えるのは、**正常例を通し、既知の不良例を落とせると数値で示せたとき**だけです。

- **不良例の作り方:** 正常な出力に人工的に不良を入れます。黒フレーム挿入、数フレームの静止、音声を数百ミリ秒ずらす、単語の読みを誤ったかなに差し替えて合成、長すぎるラベルで文字をはみ出させる、台本の数値を出典と違う値に書き換える、キーフレームを別人物に差し替える、フレームを間引いてちらつかせる、など。**どこに何を入れたかが分かっているので、正解ラベルが確実**です。これに、実運用で出た本物の不良を追加していきます。
- **測るもの:** 検査ごとの検出率（不良を落とせた割合）と誤検出率（正常を落とした割合）。
- **運用への反映:**
  - 基準を満たした検査 → その検査の合格を自動通過の根拠にできる
  - 満たさない検査 → 結果は参考扱い。その検査が担当する不良については、**安全側の経路（格下げの階段の下の段）を自動で選ぶ**
- モデル、プロンプト、しきい値を変えたら校正セットを必ず流し直します。

### 5.5 人の関与の位置づけ

全動画の人手監修は必須工程にしません。人が関わるのは次の3点です。

1. **好みの選択**（作風、声、テンポ。7章）と除外条件の設定。
2. **抜き取り確認:** 完成動画から一部を選んで見て、検査が見逃した不良を記録します。見逃しがあれば、それを校正セットに追加し検査を直します。見逃しが出ない状態が続けば、抜き取りの割合を下げます。
3. **検査が判断不能と報告したものだけの確認。**

校正セットで測れるのは「既知の種類の不良」だけです。未知の種類の不良は抜き取りでしか見つからないため、抜き取りをゼロにはしない設計にしています。

### 5.6 投稿規約に関する設計上の注意

- YouTube は、実写と誤認され得る合成映像に開示を求め、明らかに非現実的な表現には求めていないとされます【二次：公式ヘルプのスニペット】。写実系の生成映像には開示の印を台帳に持たせます。
- 収益化ポリシーは、大量生産・反復的・テンプレート的な内容を対象外としています（2025年7月に名称変更、2026年7月に再整理との報道）【二次】。**自動化するほどこの規定に近づく**ため、題材の重複排除、独自の切り口、出典に基づく内容、作品ごとの演出の差を、題材選定と構成の段階で仕組みとして確保します。長時間の語り＋生成静止画の量産型（7章の注意例）はこの規定の典型的な対象です。
- 文化庁の考え方では、画風そのものは保護されず、類似性と依拠性で判断されるとされます【二次】。参考作品からは構成とテンポを学び、特定作品の表現の再現や、特定作品で作ったLoRAは使いません。

## 6. 開発計画の詳細

各段階の「測るもの」は、次の段階の設計を決める実測値です。期間は、既存資産の状態を見ていない現時点では見積もりません。

**段階0 棚卸し（読み取りのみ）**
- 既存の台本パッケージの実物、音声エンジン、Remotion部品、既存検査の指示文を確認
- Strata の機能確認：JSONスキーマ拘束、アンロードAPI、読み込み時間、1段軽い量子化の有無
- Qwen3.8-Flash-Next と使用中の音声のライセンス原文確認
- 成果物：既存資産の再利用／作り直しの仕分け表

**段階1 接続**
- 制作台帳のスキーマ確定、既存台本パッケージからの変換器
- 演出計画の生成（大型LLM、形式拘束＋プログラム検証）
- 図解部品を「型＋プロパティ」で呼べるように整理
- オーケストレーター最小版（工程の状態、再開、実行台帳）
- 測るもの：工程ごとの所要時間、形式エラー率、人手が入った箇所の一覧

**段階2 検査と修正**
- 5.2節の検査 1〜4、9、10 を実装、校正セット作成、修正経路表
- 既存の指示文比較の仕組みを校正セット評価に接続
- 測るもの：検査ごとの検出率・誤検出率、自動修正で直った割合

**段階3 映像モデル比較**（ここでダウンロード開始。事前に承認をいただきます）
- ライセンス原文確認 → ComfyUI導入 → 候補を1つずつ同一課題で実測
- 小型VLM候補の比較も同時に（点検の校正セットで）
- 測るもの：3.2節の4区分、モデル切り替え時間
- この結果で、生成映像系の尺・ショット設計・一晩の生産量が決まる

**段階4 題材の自動選定と無人運転（解説系）**
- 題材発見の取得器、採点、題材台帳、調査の自動化
- GPU排他スケジューラ完成版、連続実行
- 尺の拡張：長尺は章単位で生成・検査・レンダリングし、最後に結合。60分級は「章の本数が増えるだけ」の構造にする
- 測るもの：無人完走率、抜き取りでの見逃し、1本あたりの総時間

**段階5 生成映像系の最小版**
- 設定書、キーフレーム生成、映像生成の投入と回収、テイク選別、格下げの階段、音楽主導の組立
- 検査 5、6、8 を実装し校正
- 測るもの：歩留まり、ショットあたりの撮り直し回数、階段のどの段で止まったかの分布

**段階6 人物と台詞**
- 参照編集によるキーフレーム → 不足なら画像LoRA
- 口の同期：映像モデルの内蔵機能（Kandinsky 6、LTX-2.5）と、InfiniteTalk（Apache-2.0、16GBの公式値なし）【一次】を比較
- 検査 7 を実装し校正

**段階7 専用化・小型化**
- 4.2節の条件に従って課題ごとに判断、学習、固定評価セットで採否

## 8. 制作過程の動画化

- **素材は実行台帳から自動で出ます。** 修正前後の比較、不良例の一覧、候補モデルの同一課題の並び、所要時間やVRAMのグラフは、台帳から Remotion で直接図解にできます。
- **撮影は節目だけ。** 画面収録は、初回の一貫動作、モデル比較、検査が不良を捕まえる瞬間、無人運転の一晩、に限ります。各回の前に「この回で見せる実測値」を決めておきます。
- **このシステム自身に作らせる。** 制作過程の解説は「出典（＝自分の実行記録）に基づく図解解説」なので、解説系の最初の実題材として適しています。段階1の完成確認を兼ねられます。
- 各回の候補：①何を作るか（この文書）、②台本から動画がつながるまで、③検査を検査する、④16GBで映像モデルを比べる、⑤一晩の無人運転、⑥最初の生成映像作品、⑦小型モデルを育てるかどうかの判定。
- 画面収録に個人情報（パス、アカウント名、APIキー）が映らないよう、表示用の作業フォルダを分けておきます。
