# アナリティクスのデータ取得（YouTube Analytics API / Reporting API）

> 対象: 自分のチャンネルの視聴データ（再生回数・総再生時間・維持率・インプレッション・CTR など）をプログラムで取り込むための仕様。OAuth スコープ、クォータ、レポートの種類、データの遅れ、保存期間、データ保存のポリシー。指標の意味そのものは扱わない。
> 使う場面: 分析工程（P5）の「視聴データの取り込み」を実装するとき、取り込みが止まったり数字が合わなかったりしたとき。
> 調査日: 2026-11-20 ／ mc_version: 対象外（MCに依存しない）
> 関連: [アナリティクス指標.md](アナリティクス指標.md)（指標の定義と見方）, [API投稿.md](API投稿.md)（Data API の投稿・OAuth・クォータ）, [ショートの仕様.md](ショートの仕様.md), [推薦の仕組み.md](推薦の仕組み.md)

## 要点
- 取得の手段は2つ。YouTube Analytics API は期間・指標・ディメンションを指定してその場で集計を返す「ターゲット クエリ」、YouTube Reporting API は1日分ずつのレポート（.csv ファイル）を毎日生成させてダウンロードする「一括レポート」。【一次】[S1][S7]
- **インプレッション数とインプレッションのクリック率（CTR）について、公式資料で API での対応が書かれているのは Reporting API のリーチレポートだけ。** 2026-01-15 に追加された `channel_reach_basic_a1` / `channel_reach_combined_a1` で、指標名は `video_thumbnail_impressions` と `video_thumbnail_impressions_ctr`。Analytics API で取れるかは資料の間で食い違う（詳細の節）。【一次】[S1][S8][S10]
- **維持率（視聴者維持のグラフ）は Analytics API で1本ずつ取る。** `elapsedVideoTimeRatio` ディメンションで動画1本につき100点が返り、video フィルタには動画IDを1つしか指定できない。Reporting API のチャンネル向けレポート一覧に維持率のレポートはない（2026-11-20 に一覧を確認）。2016-06-22 の変更履歴にも、Reporting API の `elapsed_video_time_percentage` と `audience_retention_type` は利用できるレポートでサポートされていないとある。【一次】[S3][S5][S8][S10]
- データは即時ではない。Analytics API の元データには通常48〜72時間の遅れがあり、すべての指標がそろった最終日までしか返らない。リアルタイムの再生回数などは Data API の `videos.list` を使うよう公式が勧めている。【一次】[S2][S6]
- Reporting API は、ジョブを作ってから48時間以内に取得を始められる。公式の例では、ある日のレポートは2日後に作られる（保証された遅れの上限ではない）。過去分の自動生成はジョブ作成前の30日分だけ。**レポートは生成から60日（過去分は30日）で取得できなくなる**。【一次】[S7][S10]
- OAuth スコープは `yt-analytics.readonly`（収益を含めるなら `yt-analytics-monetary.readonly`）。reports.query のページには `youtube.readonly` が必要という注記もある。収益指標は YPP 未参加のチャンネルでは 403 になる。【一次】[S2][S3][S11]
- サービスアカウントとデバイス用フロー（入力が限られた機器向け）は両 API とも使えない。reports.query のページの Python サンプルは、パソコン用アプリのフロー（`InstalledAppFlow`）で書かれている。【一次】[S2][S11]
- 同意画面が外部ユーザー・テスト中のプロジェクトでは、更新トークンが7日で期限切れになる。6か月使われていないことも、更新トークンが使えなくなる理由に挙がっている。【一次】[S12]
- クォータ: Analytics API はデータモデルのページでは1リクエスト1ユニット（上限は Cloud コンソールで確認）。ただし両 API を比べたページには「API サーバーは各クエリを評価して、割り当て費用を決定します。」ともある。Reporting API は一度落とせば手元で処理するのでクォータは問題にならない、と公式は説明している。【一次】[S1][S6]
- ショートの視聴回数の数え方は2025-03-31に変わり（再生・リプレイの開始を数える）、旧来の数え方は `engagedViews` / `engaged_views` に残された。2026-08-27 の変更履歴では全フォーマットの公開視聴回数を再生開始で数える方式に統一すると告知され（適用日の記載なし）、2026-11-16 からは共視聴（テレビで複数人が見る）が公開視聴回数と総再生時間に含まれる。**時系列で比べるなら定義の変わり目に注意。**【一次】[S4][S10]
- 日付の区切りは太平洋時間。日本時間の0時区切りではない。【一次】[S5][S7]
- Analytics API と Reporting API で取得したデータは、利用者が明示的に同意した目的に使う限り必要な期間保存してよいが、30日を超えて保存するなら30日ごとに利用者の許可が続いていることを確かめる（デベロッパー ポリシー）。【一次】[S14]

## 詳細

### 2つの API の違い
両 API とも、チャンネル所有者とコンテンツ所有者のレポートに対応し、すべてのリクエストはデータを所有するチャンネル（またはコンテンツ所有者）の承認が必要。【一次】[S1]

| 項目 | YouTube Analytics API | YouTube Reporting API | 確度・出典 |
|---|---|---|---|
| 取り方 | リクエストごとにディメンション・指標・期間を指定 | レポートジョブを予約し、YouTube が日次レポートを生成、それを非同期でダウンロード | 【一次】[S1] |
| 期間の集計 | 月単位などの集計ディメンションがある | すべて日単位。期間の集計は自分で実装 | 【一次】[S1] |
| フィルタ・並べ替え | API 側でできる | できない。全データを落として手元で処理 | 【一次】[S1] |
| 列挙値 | テキスト（`ANDROID`、`CHANNEL` など） | 整数（テキストに対応づける） | 【一次】[S1] |
| クォータ | クエリごとに費用を評価 | 問題にならない | 【一次】[S1] |
| 名前の付け方 | camelCase（例: `adType`） | 小文字とアンダースコア（例: `ad_type`） | 【一次】[S1] |

> 「データは 1 回取得されてから、アプリケーション内でフィルタリング、並べ替え、クエリが行われるため、割り当ての使用量は問題になりません。」[S1]

主な指標・ディメンションの名前の対応（取り込みで使うもの）。`engagedViews` / `engaged_views` の行以外は [S1] の対応表から。【一次】[S1]

| Analytics API | Reporting API |
|---|---|
| `views` | `views` |
| `engagedViews`（[S4]） | `engaged_views`（[S8] の channel_basic_a3）※[S1] の対応表には載っていない |
| `estimatedMinutesWatched` | `watch_time_minutes` |
| `averageViewDuration` | `average_view_duration_seconds` |
| `averageViewPercentage` | `average_view_duration_percentage` |
| `audienceWatchRatio` | `audience_retention_percentage` |
| `elapsedVideoTimeRatio` | `elapsed_video_time_percentage` |
| `insightTrafficSourceType` | `traffic_source_type` |
| `video` | `video_id` |
| `day` | `date` |
| `videoThumbnailImpressions` | `video_thumbnail_impressions` |
| `videoThumbnailImpressionsClickRate` | `video_thumbnail_impressions_ctr` |

この対応表には Analytics API 側の名前として `videoThumbnailImpressions` が載っているが、同じ資料のレポートの種類の表ではリーチレポートはチャンネル・コンテンツ所有者とも一括（Reporting API）のみ対応とされ、Analytics API の指標ページ（2026-11-16 更新）とチャンネル レポートのページにもこの指標は見当たらない（2026-11-20 にページ内を検索して確認）。【一次】[S1][S3][S4]

同様に、対応表には `elapsedVideoTimeRatio` → `elapsed_video_time_percentage`、`audienceWatchRatio` → `audience_retention_percentage` も載っているが、2016-06-22 の変更履歴では Reporting API の `elapsed_video_time_percentage` と `audience_retention_type` はディメンションの一覧から外され、利用できるレポートではサポートされていないとされている。【一次】[S1][S10]

### 認可（OAuth のスコープとフロー）
- Analytics API のエンドポイントは `GET https://youtubeanalytics.googleapis.com/v2/reports`。必須パラメータは `ids`・`startDate`・`endDate`・`metrics`。自分のチャンネルは `ids=channel==MINE` で指定できる。【一次】[S2]
- Analytics API で使うスコープは `yt-analytics.readonly`（再生回数や評価などのユーザー アクティビティ指標）、`yt-analytics-monetary.readonly`（それに加えて推定収益と広告の指標）、`youtube`・`youtubepartner`（グループの管理用）。Reporting API は前の2つ。認可ガイドの Analytics API のスコープ一覧には `youtube.readonly`（YouTube アカウントの表示）も載っている。【一次】[S2][S7][S11]
- reports.query のページには次の注記がある。2018-06-18 の変更履歴にも同じ変更が載っている。【一次】[S2][S10]
> 「重要: このメソッドに対する API リクエストでは、https://www.googleapis.com/auth/youtube.readonly スコープへのアクセスが必要になりました。」[S2]
- ただし同じページの Python サンプルは `SCOPES = ['https://www.googleapis.com/auth/yt-analytics.readonly']` だけで書かれている。【一次】[S2]（実際にどちらで動くかは『わかっていないこと』の節へ）
- 収益指標は monetary スコープで承認され、かつ YPP のメンバーであるときだけ返る。【一次】[S3]
> 「YouTube パートナー プログラムに参加していないチャンネルの収益指標をリクエストすると、403 Forbidden エラーが発生します。」[S3]
- 使えない認可フロー: 入力が限られたデバイス向けのフローとサービスアカウントのフロー。【一次】[S11]
> 「The YouTube Reporting and YouTube Analytics APIs do not currently support the OAuth 2.0 flow for devices.」[S11]
> 「ただし、YouTube Reporting API と YouTube Analytics API はこのフローをサポートしていません。」[S11]（サービスアカウントについて）
> サービスアカウントを YouTube アカウントに結びつける方法がないため、このフローで承認しようとするとエラーになる（訳）。原文:「Since there is no way to link a Service Account to a YouTube account, attempts to authorize requests with this flow will generate an error.」[S11]
- 更新トークンが使えなくなる条件（Google の OAuth 2.0 全般の説明）: 利用者がアクセス権を取り消した、6か月使われていない、アカウントあたりの発行数の上限を超えた、など。外部ユーザータイプで公開ステータスがテストの同意画面では、名前・メールなどの基本スコープだけの場合を除き、「7 日で期限切れになる更新トークンが発行されます」。【一次】[S12]
> 「更新トークンが 6 か月間使用されていない。」[S12]
- 更新トークンは OAuth クライアント ID ごと・Google アカウントごとに100個が上限で、超えると最も古いものが警告なしに無効になる。【一次】[S12]
- 機密性の高いスコープを使い、Google の確認（verification）を受けていないアプリには未確認アプリの警告画面が出ることがある。開発中・テスト用のアプリは公開しない限り確認は不要。【一次】[S13]
- 同じページに、利用者が自分1人だけのアプリ向けの Personal mode が書かれている。Personal mode の作成ページから作ったアプリは自分の Google アカウントだけに制限され、未確認アプリの画面が出ず、確認も要らない（訳）。原文:「If you are the only user of your app and you create your app using the Personal mode onboarding page, your app is restricted exclusively to your Google Account, does not display the unverified app screen, and does not need to go through verification.」【一次】[S13]

### クォータ
- Analytics API: データモデルのページ（2026-11-05 更新）にこう書かれている。【一次】[S6]
> 「API リクエストは、1 回ごとに API 使用量割り当ての 1 ユニットとしてカウントされます。」[S6]
- 一方、2つの API を比べたページ（2026-09-15 更新）には「API サーバーは各クエリを評価して、割り当て費用を決定します。」とあり、2012-09-12 の変更履歴には、クエリの費用がレポートの種類で大きく違うという説明がある。最も新しく更新されたデータモデルのページ（2026-11-05）は1リクエスト1ユニットと書いており、資料の間で書き方がそろっていない。【一次】[S1][S6][S10]
- Analytics API の既定の上限値は、読んだ資料には書かれておらず、Cloud コンソールの割り当てのパネルで確かめるよう案内されている。【一次】[S6]
- 参考: Data API（`videos.list` など）は、既定で1日あたり `search.list` 100回、`videos.insert` 100回、それ以外のエンドポイント合計で10,000ユニット。`videos.list` は1回1ユニット。【一次】[S15]
> 「1 日の割り当ては、太平洋時間（PT）の午前 0 時にリセットされます。」[S15]
- クォータの上限に達した API クライアントは、API コンプライアンス監査を受けて割り当ての延長を申請できる。【一次】[S14]
> 「API プロジェクトが 90 日間連続して非アクティブな状態である場合、YouTube は特定の YouTube API サービスへのアクセスまたは使用を無効にするか、制限する権利を有します。」[S14]

### データの遅れと日付の区切り
- Analytics API の遅れについては、2026-09-09 にデータモデルのページへ専用の節が追加された。【一次】[S10]
> 「データ処理では通常、48 ～ 72 時間のレイテンシが発生します。」[S6]
> 「アプリケーションで、現在の視聴回数、高評価数、コメント数など、個々の動画のリアルタイム統計情報が必要な場合は、YouTube Analytics API ではなく、YouTube Data API の videos.list メソッドを使用します。」[S6]
- endDate より前の日までしかデータがそろっていなければ、レスポンスはそろっている最終日で打ち切られる。一部の指標だけ先にそろっていても、全指標がそろった日までになる（公式の例: endDate を7月5日にしても、全指標が7月3日までなら7月3日まで）。【一次】[S2]
> 「day ディメンションを含むクエリのレスポンスには、最新の日の行は含まれません。」[S2]
- API の数字と YouTube Studio のリアルタイム表示が食い違うことがあると公式が書いている。【一次】[S6]
- 日付はすべて太平洋時間で区切られる。【一次】[S5]
> 「重要: すべての日付は、指定された日の午前 12 時（太平洋時間、UTC-7 または UTC-8）から午後 11 時 59 分（太平洋時間）までの期間を指します。」[S5]
- Reporting API のレポートの説明は、太平洋標準時（UTC-8）の0時〜23時59分の24時間としている（夏時間の扱いは [S5] と書き方が違う）。【一次】[S7]
- `month` ディメンションを使うときは、開始日と終了日の両方を月の初日にする必要がある。【一次】[S5]

### Analytics API（reports.query）で取り込みに効く仕様
- レスポンスは JSON で、`columnHeaders`（ディメンションが先、指標が後、リクエストの順）と `rows` を返す。該当データがなければ `rows` 自体が省かれる。v2 では CSV 出力（`alt`）は使えない（`alt` は v2 ではサポートされず JSON のみ）。【一次】[S2]
- video・playlist・channel のフィルタには、カンマ区切りで最大500個の ID を指定できる。そのフィルタを dimensions にも入れると、ID ごとに分けて返る。【一次】[S2][S6]
- 人気動画のレポートは `maxResults` を200以下にし、`sort` の指定も必須。トラフィック ソースの詳細（`insightTrafficSourceDetail` による参照元の内訳）は25以下で `sort` 必須。【一次】[S3]
> 「注: これらのレポートでは、maxResults パラメータを 200 以下の整数値に設定する必要があります。」[S3]
- サポートされない組み合わせや必須パラメータの欠けは、HTTP 400 badRequest（The query is not supported）になる。【一次】[S3][S10]
- `creatorContentType` ディメンションで `LIVE_STREAM`・`SHORTS`・`STORY`・`VIDEO_ON_DEMAND` を分けられる。2019-01-01 以降のデータが対象。【一次】[S5]
- 動画・再生リスト・チャンネルなどを最大500個まとめた『グループ』単位でもデータを取れる。【一次】[S6]
- 削除した動画は、動画別のレポートからは消えるが、まとめた合計には残る。そのため日別合計と動画別の合計が合わないことがある。【一次】[S6]
- トラフィックが少ないとき、またはしきい値に届かない国・トラフィック ソースなどで絞ったとき、データの一部または全部が出ないことがある。年齢・性別、地域、検索語句や外部 URL が対象になりうる。【一次】[S6]
> 「注: データが限定的になる実際のしきい値は公開されておらず、YouTube の裁量で変更される可能性があります。」[S6]

### 維持率（視聴者維持）の取り方
- レポートの形（Analytics API のチャンネル レポート『視聴者維持率』）。【一次】[S3]

| 区分 | 内容 |
|---|---|
| ディメンション（必須） | `elapsedVideoTimeRatio` |
| 指標（1つ以上） | `audienceWatchRatio`, `relativeRetentionPerformance`, `startedWatching`, `stoppedWatching`, `totalSegmentImpressions` |
| フィルタ（必須） | `video` |
| フィルタ（任意） | `audienceType`, `subscribedStatus`, `youtubeProduct` |

> 「注: このレポートでは、video フィルタにカンマ区切りの値のリストを指定することはできません。値には単一の動画 ID を指定する必要があります。」[S3]
- データ点の数と間隔。【一次】[S5]
> 「この API は、各動画について 100 個のデータポイントを返します。比率の値は 0.01 から 1.0 の範囲です。」[S5]
- 点の間隔は動画の長さの1/100で、2分の動画なら1.2秒、2時間の動画なら72秒。【一次】[S5]
- `audienceWatchRatio` は、その時点を見た回数を動画の総視聴回数で割った絶対的な比率。巻き戻して見直されると1を超える。【一次】[S4]
> 「たとえば、ユーザーが動画の同じ部分を巻き戻して複数回視聴した場合、動画のその部分の絶対比率は 1 を超える可能性があります。」[S4]
- `relativeRetentionPerformance` は長さが同程度の他の YouTube 動画との比較で、0.5 が中央値。【一次】[S4]
> 「この指標の値は 0～1 で、動画の特定の時点における相対的な視聴者維持率を示します。」[S4]
- `startedWatching` / `stoppedWatching` は、その区間が視聴の最初・最後の区間になった回数。どこで離脱されたかを数で見るのに使える。【一次】[S4]
- `audienceType` は `ORGANIC`・`AD_INSTREAM`・`AD_INDISPLAY` のどれかで、広告経由の視聴を分けられる（2013-09-25 以降のデータ）。【一次】[S5]

### インプレッションとクリック率の取り方（Reporting API のリーチレポート）
> 「YouTube Reporting API で、チャンネルとコンテンツ所有者のリーチ レポートがサポートされるようになりました。」[S10]（2026-01-15 の項目）

| レポート ID | ディメンション | 指標 | 確度・出典 |
|---|---|---|---|
| `channel_reach_basic_a1` | date, channel_id, video_id | video_thumbnail_impressions, video_thumbnail_impressions_ctr | 【一次】[S8] |
| `channel_reach_combined_a1` | date, channel_id, video_id, traffic_source_type, traffic_source_detail, operating_system, device_type | 同上 | 【一次】[S8] |

- インプレッションの数え方: サムネイルの50%以上が1秒以上画面に出たとき。CTR はクリック数をインプレッション数で割ったもの。【一次】[S9]
> 「インプレッションがカウントされるのは、サムネイルの 50% 以上が 1 秒以上画面に表示された場合です。」[S9]
- 2026-08-27 の変更履歴では、サムネイルのインプレッションは変更なしとされ、用途は「フィードレベルの露出とパッケージングを測定します。」と説明されている。【一次】[S10]
- 基本の動画レポート `channel_basic_a3` のディメンションは date, channel_id, video_id, live_or_on_demand, subscribed_status, country_code で、指標に engaged_views、views、watch_time_minutes、average_view_duration_seconds、average_view_duration_percentage、subscribers_gained などを含む。インプレッションは含まない。【一次】[S8]

### Reporting API の流れと保存期間
1. `reportTypes.list` で作れるレポートの ID を調べる（例: `channel_basic_a3`）。【一次】[S7]
2. `jobs.create` でジョブを作る。ジョブを作るまでレポートは生成されない。【一次】[S7]
3. `jobs.reports.list` で、ジョブのレポートの一覧（`startTime`・`endTime`・`createTime`・`downloadUrl`）を取る。`createdAfter` で未処理のものだけに絞れる。【一次】[S7]
4. `downloadUrl` に GET してダウンロードする。`Accept-Encoding: gzip` で圧縮できる。【一次】[S7]

> 「ジョブの作成から 48 時間以内にレポートの取得を開始できます。最初に利用可能になるレポートは、ジョブをスケジュールした日のレポートです。」[S7]
> 「たとえば、9 月 1 日にジョブをスケジュールした場合、9 月 1 日のレポートは 9 月 3 日に作成されます。」[S7]
- データがない日も、ヘッダー行だけのレポートが作られる。【一次】[S7]
- 保存期間: 通常のレポートは生成後60日、ジョブ作成時に作られる過去分のレポートは生成後30日で取得できなくなる。【一次】[S7]
> 「レポートは、作成から 60 日を超えるとアクセスできなくなります。」[S7]
- 過去分: 2018年7月の変更以降、ジョブを作るとその時点から30日前までの期間のレポートが作られる（それ以前は180日前まで）。過去分は通常数日以内にそろう。【一次】[S7][S10]
- バックフィル（以前に配ったデータの差し替え）は、同じ `startTime`・`endTime` をもつ新しい ID のレポートとして届く。【一次】[S7]
> 「ただし、2 つの新しいレポートの startTime プロパティと endTime プロパティの値が同じ場合は、createTime 値が新しいレポートのみをインポートします。」[S7]

### 取り込み処理で気をつけること
- 列の順番はレポートのヘッダー行で決める。新しい指標が列として増えることを前提に作る。これは両 API の公式のベストプラクティス。【一次】[S6][S7]
- 2025-06-24 の変更履歴では、ショートの視聴回数の変更に合わせて視聴回数を含むレポートの大部分の版が1つ上がり（a2→a3 など）、古い版は廃止された（廃止日は 2025-09-30 から 2025-10-31 に延期）。レポート ID の末尾の版は変わることがある。【一次】[S10]
- 一括レポートには、指標のない行（その日の再生が0の国など）と、合計の行が入らない。合計は自分で足すか Analytics API で取る。【一次】[S7]
> 「レポートでは、指標のない行は省略されます。」[S7]
- `video_id` が空文字の行がありうる。削除された動画の分や、チャンネルのホームからの登録などチャンネル単位で起きた指標がそうなる。【一次】[S7]
- レポートの生成日の30日以上前に削除されたリソースへの参照は入らない。【一次】[S7]
- 匿名化: 検索語句などは、その動画のその日の視聴回数がしきい値以上のときだけ出て、残りは NULL の1行にまとめられる。説明の例ではしきい値を10としているが、実際の値は変わることがある。【一次】[S7]

### 視聴回数の定義の変更（取り込んだ時系列に影響）
> 「最低総再生時間の要件がなくなり、ショート動画の再生および繰り返し再生が開始された回数が視聴回数としてカウントされるようになります。」[S10]（2025-03-26 の項目。開始は 2025-03-31）
- Analytics API は 2025-04-30、Reporting API は 2025-06-30 からこの新しい数え方になり、旧来の数え方は `engagedViews` / `engaged_views` として残された。【一次】[S10]
- `engagedViews` の定義は、動画が最初のフレームを超えて視聴された回数、またはクリック・タップで再生された回数。【一次】[S4]
- 2026-08-27 の項目: 長尺・ライブ・ショートのすべてで、再生が始まった時点で公開視聴回数として数える方式に統一すると告知した（項目内に適用日の記載はない）。YPP の収益化と、CTR・平均視聴時間など主要な分析の大部分はエンゲージ ビューに基づく、と同じ項目の表に書かれている。【一次】[S10]
- 2026-11-16: 共視聴が全フォーマットの公開視聴回数と総再生時間に含まれるようになった。【一次】[S10]
> 「クリエイターの収益、広告収入、YouTube パートナー プログラムの資格要件に影響はなく、エンゲージ ビューに共視聴は含まれません。」[S10]
- 2026-03-09: `ageGroup` / `age_group` に、YouTube が18歳未満と推定する利用者が含まれるようになった。【一次】[S10]

### 取り込んだデータの保存（YouTube API サービスのデベロッパー ポリシー）
- Analytics API と Reporting API で得たデータ、および視聴回数などの統計は、利用者が同意した目的に使う限り必要な期間保存してよい。ただし条件がある。【一次】[S14]
> 「API クライアントがこのデータを 30 日を超えて保存する場合でも、クライアントは 30 日ごとに、そのデータにアクセスする権限がユーザーから付与されていることを確認する必要があります。」[S14]
- 同じ節の例では、視聴回数を30日以上保存する場合、30日ごとに動画が削除されていないことも確認する必要があるとされている。【一次】[S14]
- 一方、レポートに出てくる動画 ID などから Data API で取ったメタデータ（タイトルなど）は、30日たったら削除するか更新する。【一次】[S6][S7][S14]
- 利用者が同意を取り消したら、その同意で得たデータは取り消しから7暦日以内に削除する。【一次】[S14]

## このチャンネルでの使い方（提案）
> ※この節は上の事実から導いた提案で、事実ではない。

- **最初の動画を出す前に Reporting API のジョブを作っておく。** 過去分は作成時点から30日前までしか作られず、レポートは60日で消えるので、遅れて作ると取りこぼす。最低限 `channel_basic_a3` と `channel_reach_basic_a1`（必要なら `channel_reach_combined_a1`、`channel_traffic_source_a3`）。（根拠: [S7][S8][S10]）
- **取り込みは毎日1回、太平洋時間の区切りを前提にする。** Analytics API は endDate を今日の3日前程度にし、返ってきた最終日を記録する。数日前の分も毎回取り直して上書きすると、遅れて確定した値も拾える。（根拠: [S2][S5][S6]）
- **Reporting API のダウンロード済み CSV は生のまま保存し、レポート ID と createTime で重複を管理する。** 同じ期間の新しいレポートが来たら、その期間の行を消して入れ直す。列はヘッダー名で読む。（根拠: [S7]）
- **CTR を数日分まとめるときは、日ごとの CTR を単純平均せず、インプレッションで重み付けする**（Σ(インプレッション×CTR)÷Σインプレッション）。CTR はクリック数÷インプレッション数なので、この計算で期間全体のクリック数÷インプレッション数に戻る。（根拠: [S9]）
- **維持率は動画ごとに、公開後の決まった日（例: 7日後・28日後）に1リクエストずつ取る。** 100点なので、10分の動画なら6秒刻み。台本のどの場面で `stoppedWatching` が増えたかを見て、場面ごとの離脱を探す。長さの違う動画どうしの比較には `relativeRetentionPerformance` を使う。（根拠: [S3][S4][S5]）
- **ショートと長尺を比べる指標、過去と比べる指標は `engagedViews` に統一する。** `views` の定義は2025-03-31・2026-11-16 に変わり、2026-08-27 にも数え方の統一が告知されている。取り込んだデータには、どの定義の時期かがわかるよう取得日を付けておく。（根拠: [S4][S10]）
- **認証は自宅PCでのインストール型アプリのフロー。** テスト中のままだと7日ごとに同意し直しになるので、Personal mode か本番公開を検討する。トークンが失効したら（`invalid_grant` など）取り込みを止めて人に知らせる仕組みにする。（根拠: [S11][S12][S13]）
- **収益の指標は YPP に入るまで要求しない**（403 になる）。スコープも最初は `yt-analytics.readonly` だけにし、入ってから monetary を足す。（根拠: [S3][S11]）
- **リアルタイムに近い再生回数（公開直後の伸び）は Data API の `videos.list`（1ユニット）で別に取る。** Analytics API の値とはずれる前提で、両方を混ぜずに保存する。（根拠: [S6][S15]）
- **毎日の取り込みが30日ごとの権限確認も兼ねるようにする**（トークンの更新に成功したことを記録する）。Data API で取ったタイトルなどは30日ごとに取り直す。（根拠: [S14]）
- **実装で効く数値やパラメータ名は、英語版（`?hl=en`）のページでも確かめる。** 日本語版は AI 翻訳で、誤りが含まれうると冒頭に注記されている。（根拠: [S1]）

## わかっていないこと・要確認
- reports.query に `youtube.readonly` が本当に必要か。ページの注記は必要と言い、同じページのサンプルは `yt-analytics.readonly` だけで書かれている。実際に両方の組み合わせで試す。
- Personal mode で作ったアプリでも、テスト中のアプリと同じく更新トークンが7日で失効するのか。[S13] にも [S12] にも書かれていない。
- `yt-analytics.readonly` が機密性の高いスコープ（sensitive）に当たるか。読んだ資料では確認できなかった。
- Analytics API の既定のクォータ上限の数値（Cloud コンソールで確認する）。資料の間で費用の書き方が違う点（1リクエスト1ユニットか、クエリごとの評価か）。
- Analytics API で `videoThumbnailImpressions` が使えるか。名前の対応表には載っているが、指標ページとレポート一覧には載っていない。実際にクエリして確かめる。
- リーチレポートのインプレッション・CTR が YouTube Studio に出る値と一致するか。ショートのインプレッションが含まれるか。
- ショート動画の維持率が `elapsedVideoTimeRatio` のレポートで取れるか、ループ再生がどう数えられるか。資料に記述がなかった。
- Reporting API の日次レポートが2日後に作られるのは例として書かれているだけで、保証された遅れの上限は書かれていない。実際の到着時刻を記録して確かめる。
- 2026-08-27 の変更履歴で告知された、全フォーマットの公開視聴回数を再生開始で数える方式への統一が、いつから API の `views` に反映されたか（項目内に適用日がない）。
- Analytics API の `audienceWatchRatio` に相当する維持率が、Reporting API で取れる形が今あるか。名前の対応表には載っているが、2016-06-22 の変更履歴ではサポートされていないとされ、チャンネル向けレポート一覧にもない。
- Studio の詳細モードから書き出せる形式（CSV・Google スプレッドシートなど）と、書き出しで取れる指標の範囲。チャンネル所有者向けのヘルプで確認できなかった。
